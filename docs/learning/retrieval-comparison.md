# 检索方式对比

## grep / file_search（确定性搜索）

| 维度 | 说明 |
|---|---|
| **作用** | LLM 明确知道要找什么关键字时，精确命中 |
| **成本** | 极低。系统调用 + 文本扫描，无模型开销 |
| **边界** | LLM 必须能猜对关键词。不知道用啥词搜时无效 |
| **典型场景** | "prefer_things.md 里 language 设了什么" → grep language |
| **LLM 可控性** | 完全可控。LLM 可调整搜索词反复试，结果确定可解释 |

## 记忆检索（Memory Retrieval）

| 维度 | 说明 |
|---|---|
| **作用** | 从已结构化的信息片段中检索，按类别/时间/关键词筛选 |
| **成本** | 低。SQLite FTS5 全文索引或简单 key-value 查表 |
| **边界** | 只覆盖 agent 主动记住的内容。没存过就查不到 |
| **典型场景** | "之前我说过喜欢什么语言" → 查 memories 表 WHERE category='preference' |
| **LLM 可控性** | 中。可通过类别/时间范围缩小搜索，但检索策略由代码固定 |

## RAG（语义检索）

| 维度 | 说明 |
|---|---|
| **作用** | 在大量未知文档中做语义匹配，找到"说不清但相关"的内容 |
| **成本** | 高。embedding 模型调用 + 向量数据库存储 + 相似度计算，每次检索都有推理成本 |
| **边界** | 需要建索引、分块、调参数。结果不确定（top-k 可能不准），LLM 无法 debug |
| **典型场景** | "这篇论文的方法论和之前哪篇客户方案相关" → 语义相似度匹配 |
| **LLM 可控性** | 低。检索是黑盒，LLM 不能调整策略，只能接受 top-k 结果 |

## 在个人助手 agent 中的适用性

```
命中率:   grep ≈ 记忆 > RAG
成本:     grep < 记忆 << RAG
可解释性: grep > 记忆 >> RAG
LLM 控制: grep > 记忆 >> RAG
适用场景: grep + 记忆 覆盖 90%+ 的个人助手需求
```

个人助手本质是"已知信息的取用"——要么 LLM 知道自己要搜啥（grep），要么是 agent 主动记住的（记忆）。RAG 解决的是"海量未知文档的盲搜"，个人助手没有这个场景。

**RAG 何时值得引入：**

1. 接入外部知识库（公司文档、论文库、Obsidian 笔记）
2. 文档量 > LLM 上下文窗口能手动浏览的量级
3. 用户无法/不愿用关键词表达需求

 chips 当前阶段这三个条件都不成立，短期不需要。
