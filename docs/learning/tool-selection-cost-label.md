# 工具选择效率：从问题发现到成本标签方案

## 背景

### 问题现象

用户两次让 chips 查天气，出现了两种不同的工具调用路径：

| 路径 | 步骤数 | 过程 |
|------|--------|------|
| 路径 A | 1 步 | 直接 `web_fetch` 天气网站 |
| 路径 B | 2 步 | 先 `web_search` 搜索，再 `web_fetch` 提取 |

对于"查天气"这类已知具体 URL 即可解决的问题，路径 B 多了一次不必要的搜索调用，浪费 token 和时间。

### 根因分析

LLM 的 ReAct 循环在做**贪婪的单步决策**。给定多个工具选项时，模型倾向于选择"确定性更高"的工具（search 永远能返回结果，fetch 可能 404 或超时），而没有机制去量化"这条路径的总成本"。这是标准 ReAct 范式的已知局限：

- 每次工具选择只考虑当前步，不做多步路径规划
- 没有内置的成本/效率感知
- `temperature > 0` 导致同一请求可能产出不同策略

## 技术调研

### 学术方向

搜索了工具选择优化的相关工作，几个最相关的方向：

| 方案 | 核心思路 | 效果 |
|------|----------|------|
| **AutoTool** (arXiv 2511.14650) | 构建工具调用惯性图，预测下一步该用什么工具 | -30% 推理成本 |
| **CATS** (OpenReview) | 工具预算标签 + early stop | BrowseComp +8.4pp |
| **SPRE** (ReadyTensor) | 执行前估算每步成本，剪掉低收益步骤 | -40% token |
| **SLIM** (arXiv 2510.18939) | search 只返摘要，browse 按需深入 | <25% tool calls |
| **RE-TRAC** (arXiv 2602.02486) | 跨轨迹压缩，避免重复探索 | +15-20pp 绝对提升 |

### 方案取舍

这些方案目前都停留在论文阶段，没有成熟工程实现。直接搬论文方案：
- 收益不确定（需要领域内评测）
- 复杂度高（需要日志收集、转移概率计算等基础设施）
- 与现有 ReAct 框架耦合紧

## 最终方案：工具描述成本标签

### 思路

在工具 description 中嵌入**成本信号**和**优先级指引**，让 LLM 在工具选择时有明确的对比依据。

### 改动

```python
# web_fetch
"description": "【成本：1 步】获取网页内容，返回纯文本。...
如果已知 URL 应优先使用此工具，比 web_search 更高效。"

# web_search
"description": "【成本：2 步】搜索互联网，返回标题、链接和摘要。...
仅在不知道具体 URL 时使用；如果已知 URL 应使用 web_fetch（成本更低）。"
```

### 为什么有效

1. **描述文案是最直接的控制信号** — ToolBench 等 benchmark 确认 description 措辞对工具选择的影响远大于 tools 数组顺序
2. **零工程成本** — 不涉及框架改动，不需要新基础设施
3. **保持灵活性** — 模型仍可在需要时选 search（当确实不知道 URL 时），不削足适履
4. **与论文方案不冲突** — 未来如果要上 AutoTool 或 CATS，description 标签可以作为额外信号

### 相关文件

- `tool/builtins/web.py` — web_fetch + web_search 的 description 修改

### 后续可做的

- 收集工具选择日志，分析成本标签实际影响
- 如果效果不够，可以考虑在 agent 层做预路由（对外部工具先用规则判断是否 fetch 即可解决）
- 长期跟踪 CATS 等方案的工程化进度
